## Summary

This repeats the exercise from the [v1.18.0 update](../../docs/adr/) era
(`docs/planning/copier-template-v1-18-0-update-evaluation.md` at commit
`f75f734` / merged as #123): bump the `tmpl_python_project_kickstart` pin,
this time from `v1.18.0` to `v1.19.2`, without accepting the template's
single-project assumptions wholesale.

| Item | Value |
| --- | --- |
| Answers file | `.copier-answers.yml` |
| Current template | `https://github.com/ff-fab/tmpl_python_project_kickstart` |
| Current pin | `v1.18.0` |
| Target | `v1.19.2` (latest release) |
| Evaluation command | `uvx --from copier --with jinja2-time copier update --trust --defaults --vcs-ref v1.19.2 --skip-tasks --conflict rej .` (run in a disposable `git archive` snapshot — no history needed since Copier only reads `_commit` from `.copier-answers.yml`) |

As with v1.18.0, the simulated update produced a mix of clean, directly
usable improvements and structural regressions that would break this repo's
monorepo CI dispatch, docs/Docker matrices, and root virtual-workspace
`pyproject.toml`. The same three-part triage applies: **Direct** (byte-for-byte
or near-byte-for-byte from the simulation), **Adapt** (genuine upstream value,
hand-merged onto the monorepo-specific structure), and **Skip** (template
change doesn't apply here, or would be a regression).

## Implementation Options

| Option | What it does | Advantages | Disadvantages | Recommendation |
| --- | --- | --- | --- | --- |
| A: Direct Copier update | Apply the simulated update in place, resolve `.rej` conflicts textually. | Fastest; simplest Copier bookkeeping story. | Would replace app-matrix CI, per-app docs/Docker matrices, and the root virtual-workspace `pyproject.toml` with single-project equivalents — the same class of regression already rejected at v1.18.0. | Not recommended. |
| B: Selective monorepo-aware backport | Apply clean low-risk updates directly; hand-adapt CI/docs/release/Taskfile/qa-task changes onto the existing monorepo structure; bump `_commit` last. | Captures the real upstream value (cache correctness fix, Pages hardening, dependency currency, `docker:lint`) while preserving the architecture this repo depends on. | More manual effort per file; the template still hasn't learned this repo's shape, so the next update will need the same treatment. | **Recommended** — same choice made at v1.18.0, and the diff shape (single-project workflows vs. this repo's app-matrix ones) confirms the template still hasn't converged on monorepo support. |
| C: Defer pin bump | Leave `_commit: v1.18.0`, file the candidate list as follow-up issues. | Zero implementation risk right now. | Leaves the U5/U6/U7 devcontainer cache-correctness fix and Pages hardening on the table indefinitely; drifts further from upstream. | Not recommended — no time pressure argued for deferring, and the cache-correctness fix (U5–U7) is worth landing promptly. |
| D: Upstream monorepo support first | Contribute monorepo-awareness to `tmpl_python_project_kickstart` itself, then re-run Copier. | Best long-term ergonomics; fewer manual reconciliations on every future bump. | Out of scope for this session; separate repo, separate review cycle. | Consider separately — same conclusion as the v1.18.0 doc; the diff shape at v1.19.2 makes the case again (`ci.yml`/`docs.yml`/`release-please.yml` are *still* single-project). |
